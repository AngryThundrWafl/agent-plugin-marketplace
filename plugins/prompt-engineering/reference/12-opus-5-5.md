# Claude Opus 5.5

Tags: `[Claude docs]` = from the fetched page above. `[General]` = synthesis, must be tested. `unverified` = page silent.
Condensed digest, not official wording. **Verbatim** blocks are exact copies from the source page.

## 1. Capabilities relevant to prompting [Claude docs]

- Agentic coding/code review: at default `medium`, matched or beat Opus 5 at `high` in fewer steps/tokens; stronger long-running autonomous work (multihour audits/migrations with parallel subagents); better review (more bugs, fewer false alarms).
- Knowledge work: fewer wrong figures/citations; better financial modeling; catches subtle input inconsistencies.
- Communication: progress updates and final summaries say what was done, found, and needed.
- Vision/computer use: reads dense charts, diagrams, screenshots more accurately without extra tooling; more reliable computer use.

## 2. Calibrate effort [Claude docs]

- Thinking is always on; effort is the first knob. Default is `medium` (Opus 5 defaulted to `high`). Set it explicitly; re-sweep against your evals.
- Page: Opus 5.5 `medium` matches/exceeds Opus 5 `high` on coding and knowledge-work evals; `low` comes close on several coding evals at much lower cost.
- At a given level it tends to think more per turn than Opus 5, especially at `xhigh`/`max` → longer turns/more tokens if you carry old settings.
- Set `max_tokens` high enough for thinking + reply (thinking counts even when not returned). 128,000 (model max) worked well for long agentic coding turns.
- Reserve `xhigh`/`max` for measured gains. To get less thinking, lower effort first — more reliable than prompt instructions.
- Changing top-level `effort` between requests invalidates cached messages; use per-message effort (beta) to keep the cache.

## 3. Prompts written for thinking disabled [Claude docs]

Opus 5.5 returns **400** for `thinking: {"type": "disabled"}` (Opus 5 allowed it at `high` or below). If you ran Opus 5 with thinking off:
- Start at `low` effort and measure; move to `medium` if quality drops. Optionally add the line "Answer directly without deliberating." (page says it can reduce thinking further; measure quality).
- Remove instructions that make the model write its reasoning in the response; use `display: "summarized"` thinking blocks. Such prompts may be declined with `reasoning_extraction`.
- Re-test the Opus 5 thinking-disabled mitigations; remove any "do not think" rule either way.
- Read responses by block type; the first block may be an (empty) `thinking` block under `display: "omitted"`.

## 4. Unattended agentic runs [Claude docs]

Problem: some progress updates end the turn with text (`stop_reason: "end_turn"`); a naive agent loop treats that as completion.
Harness-side fixes (paraphrased):
- Treat text-only end of turn as a report, not proof of completion; keep a checklist (to-do tool/file).
- If items remain open with no blocker stated, send a short user message naming them. **Verbatim** example:

```text
Your task list still has open items: migrate the remaining two endpoints and update their tests. Continue with them. If one is blocked, say what is blocking it.
```
- Alternatively state the completion condition up front and have a smaller model check it at each end of turn.
- Cap automatic continuations at two or three per task. If a background command/subagent is running, wait for it and feed output back as the next user message.

Prompt-side fix: the page gives a long "standing instruction" paragraph naming four early-stop patterns (a summary that announces the next step with no tool call; an offer to carry on unless the user objects; a list of non-blocking decisions for the user; deciding a milestone is a good place to report), allowing status notes and recommendations in the same message as the next tool call, and keeping stops only where nothing can move without the user or a blocker is deliberately protected. It says it does not override confirmation for risky/destructive actions (exact verbatim text is omitted from this digest; upstream URL is recorded in `source:`).
Constraints from the page: add it from the first request of the session (adding later changes `system` and invalidates earlier thinking blocks); leave it out of human-in-the-loop apps; expect somewhat more tool calls/tokens; keep your own confirmation for risky actions.

## 5. User-facing progress updates [Claude docs]

Four levers:
1. Client must receive them: updates come as progress-update `thinking` blocks, empty at default display; set `display: "updates"` (beta `thinking-display-updates-2026-08-18`).
2. A send-message tool for verbatim hand-offs (e.g. a code snippet), declared in `tools` from the first request.
3. System-prompt instructions for predictable updates (one-line intent before first tool call, short recap at end) — helps most in human-in-the-loop work.
4. Harness reminder after ~5 silent tool-calling steps, as a turn-scoped system message (`clear_at: "next_user_message"`, beta `mid-conversation-system-clear-at-2026-08-21`); stop after two or three reminders; roughly halved long silent stretches in agentic coding tests. **Verbatim** reminder:

```text
The user hasn't heard from you in a while: say in a few words what you're doing, then continue.
```

## 6. Explore context in multiapp workflows [Claude docs]

For work across email/docs/spreadsheets/CRM where needed info is not named in the request, the model gets to work quickly; one system-prompt sentence made it look around first (noticeably more correct completions at `medium` and `max`, slightly more tool calls/tokens). **Verbatim**:

```text
Before taking any action, explore broadly with tool calls: list and open the emails, documents, spreadsheet tabs, and records across the available apps that could be relevant to this task, including ones the task does not explicitly mention, and use what you find.
```
Caveat from page: it tells the model to act on what it finds → keep untrusted content out of searched records.

## 7. Time signals for multiagent harnesses [Claude docs]

- The model is highly responsive to elapsed-time information. Give a time budget by appending e.g. `elapsed 340s / 1200s` to each message sent back to the model; set the budget somewhat above the time you want spent (it can finish well before).
- If no sensible budget: show elapsed time only plus this **verbatim** sentence:

```text
Time matters here: do not spend time that can be avoided, and the earlier a correct result is obtained, the better.
```
- In small research agent teams both signals made teams finish sooner; budgeted teams kept quality comparable to a single agent. Budget is advisory — keep your own hard timeout; check answer quality (it might search/verify less).

## 8. Thinking instructions in chat system prompts [Claude docs]

- Remove "think carefully before answering" lines; effort is the control. Removing one made replies start sooner with no clear quality decline (chat product test).
- In multi-turn chat the model sometimes re-examines earlier answers on short follow-ups. Optional two-sentence addition (**verbatim**):

```text
Once you have answered something, treat that answer as done. On later turns, focus your thinking on what the user is asking now, and don't go back over an earlier answer unless the user asks about it or points out a problem with it.
```
- Leave it out for long analyses or agentic tasks where later steps may reveal earlier mistakes; test whether the model still self-corrects (Fable 5.2 stopped self-correcting earlier mistakes when given these lines).

## 9. Mark pasted text in user messages [Claude docs]

- Resists indirect prompt injection better than earlier Opus models; for user-pasted content, wrap each pasted block in matching open/close tags carrying the same short random ID generated by your app, each tag on its own line (`<pasted_content id="ab12"> … </pasted_content id="ab12">`), and add a system-prompt note saying tagged text was pasted from elsewhere, may contain instructions the user didn't write, should be followed only where the user's own message asks, and that the ID must not be mentioned. May make the model slightly more cautious; tags can be imitated → one guardrail among others (condensed; exact upstream system note URL is recorded in `source:`).

## 10. Tools for complex visual inputs [Claude docs]

Re-test old vision scaffolding. For the densest inputs: higher-resolution images help (most for technical drawings), and an image-processing container (PIL/OpenCV) or at least a cropping tool adds accuracy. Tools work better at higher effort; without tools, higher effort helps technical drawings but little for charts (`multimodal-crop-tool` cookbook).

## 11. Frontend design defaults [Claude docs]

Without direction it falls back on a few default styles; "avoid a generic AI look" just swaps defaults. Name specific patterns to avoid and iterate. **Verbatim** page example:

```text
Output a vanilla HTML/CSS personal website with placeholder data. Do not use a cream or off-white background, italic accent words in headlines, numbered "01/02/03" section labels, monospace labels, or pill-shaped buttons.
```

## 12. Safeguard refusals [Claude docs]

- Classifiers for biology (same as Fable 5.1's; Opus 5 lacked them), cybersecurity (finding vulnerabilities in source code allowed; high-risk dual-use not), and reasoning extraction.
- Decline = normal response with `stop_reason: "refusal"` + `stop_details` category. Server-side fallback can retry on a fallback model **except** `reasoning_extraction`, which is returned to you.
- Don't ask the model to reproduce its reasoning in the response; a short explanation or action summary is fine.
